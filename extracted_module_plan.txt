THE BLING HAVEN
MODULE-WISE DEVELOPMENT PLAN
International Jewellery & Ornaments E-Commerce Platform
Admin Platform → Catalog → Storefront → Commerce → Security → Scale → Production
Reference storefront: theblinghaven.shop
Version 1.0 | 15 August 2026
1. Purpose of This Development Plan
This document breaks the large The Bling Haven international jewellery e-commerce project into controlled modules that can be designed, developed, secured, tested and accepted independently. Each module includes UI/UX, frontend, backend, database/API, security, testing and acceptance considerations.
The recommended approach is to build the security and admin foundation first, then progressively add catalog, storefront and commerce capabilities. No later module should bypass the common authentication, authorization, audit, validation, logging and monitoring foundations.
2. Core Development Principles
Build backend security together with the UI; do not treat security as a post-development activity.
Use server-authoritative pricing, inventory, permissions and payment state.
Every module must have explicit ownership, API contracts, database changes, tests and acceptance criteria.
Use least privilege and defense-in-depth for all administrative functionality.
Keep production databases, Redis and internal services on private networks.
Use CDN/WAF/DDoS/bot controls before exposing production traffic.
Design for internationalization from the beginning rather than adding locales later.
Treat high-value jewellery commerce as a fraud-sensitive environment.

4. Module 01 - Admin Login & Security Foundation
This is the first implementation module. The admin portal is the highest-impact part of the platform because compromise can expose products, customers, pricing, orders, promotions, refunds and operational controls.

4.2 Authentication Flow
Admin → WAF/CDN → Rate Limiter → Authentication Service → Credential Verification → Risk Evaluation → MFA/Step-up → Secure Session → Admin Portal
4.3 Password & Session Controls
Store passwords only as strong Argon2id hashes with unique salts and appropriate work factors.
Never store passwords, reset tokens or MFA secrets in application logs.
Reset tokens must be random, single-use and expire quickly.
Use Secure + HttpOnly + SameSite cookies when cookie sessions are used.
Use short-lived access credentials and controlled refresh/session rotation where token-based sessions are used.
Support session listing and revocation for administrators.
Require re-authentication for high-risk operations such as changing MFA, resetting credentials and high-value financial actions.
4.4 Threats Covered
Threat
Control
Brute force
Endpoint rate limiting, progressive delays, adaptive challenge
Credential stuffing
Bot detection, MFA, anomaly detection, breached-password controls where appropriate
Session hijacking
Secure session cookies, rotation, revocation, HTTPS
Account enumeration
Uniform errors and response behavior
Password reset abuse
Rate limits, token expiry, single-use tokens
Admin takeover
Mandatory MFA, least privilege, privileged monitoring
4.5 Module Acceptance Criteria
Valid authorized admin can sign in and reach only permitted admin areas.
Invalid credentials do not reveal whether an account exists.
MFA is enforced for privileged roles.
Admin session can be revoked.
Password-reset link expires and cannot be reused.
Repeated authentication abuse is throttled/blocked according to policy.
All authentication security events are logged without secrets.

20. Module 17 - Orders, Fulfillment & Tracking
Suggested order lifecycle: Pending Payment → Paid → Processing → Packed → Shipped → Delivered, with controlled branches for Cancelled, Return Requested, Returned and Refunded.
Use an explicit state machine; reject invalid transitions; snapshot commercial values at order time; protect shipment webhooks; record operator actions.

26. Module 23 - CDN, WAF, DDoS & Traffic Protection
Production traffic should follow: Internet → DNS → CDN/DDoS Protection → WAF → Bot Management → Rate Limiter → Load Balancer → Application → Private Data Network.
Keep origin IP addresses private and accessible only from approved edge/network paths.
Use endpoint-specific rate limits for login, password reset, search, cart, coupons, checkout, payments and webhooks.
Cache public catalog/content responses but never cache personalized account/order/payment responses.
Apply request body, URL, header and query complexity limits.
Use adaptive bot challenges rather than forcing challenges on every visitor.
Use circuit breakers, queue backpressure and graceful degradation for non-critical dependencies.
Maintain a DDoS incident runbook with emergency rules and escalation contacts.

28. Module 25 - Production Deployment, Backup & Disaster Recovery
Deployment pipeline: Developer → Pull Request → Code Review → Tests → Security Scans → Build Artifact → Staging → E2E/DAST → Approval → Production → Smoke Test → Monitoring.
Separate development, staging and production environments.
Use managed secrets and KMS-backed encryption where available.
Use encrypted automated backups with isolated credentials and point-in-time recovery.
Perform scheduled restore drills, not only backup jobs.
Define target RPO/RTO for the business and validate them under realistic recovery tests.
Maintain rollback and incident-response runbooks.

35. Key Principle for The Bling Haven
The project should not be treated as a collection of web pages. It is a secure international commerce platform. The admin portal, CMS, media pipeline, product system, inventory, checkout, payment, order and security monitoring are interconnected domains. The safest implementation strategy is to establish the security and administration foundation first, then build every subsequent module on top of that foundation.
